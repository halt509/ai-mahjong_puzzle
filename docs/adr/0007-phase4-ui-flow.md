# ADR-0007: 画面状態と通知を独立させローカル最高点だけを保存する

- 状態: 採用
- 日付: 2026-07-24
- 使用AIモデル: GPT-5
- 関連フェーズ: フェーズ4
- 関連仕様: `docs/PROJECT_SPEC.md` 17.1、17.2、17.4

## 背景

タイトル、通常ゲーム、川・役オーバーレイ、カン・和了通知、結果画面を追加するにあたり、Pyxelの描画分岐だけで状態を持つと、最終ターンや複数通知の遷移が不明瞭になる。また通知を読んだ後、テンポを止めずにプレイへ戻れる操作が必要だった。

## 決定

`UiState`が現在画面、通知キュー、ゲーム終了後の結果画面遷移を管理する。通知はカン、和了の順序付きデータとして1件ずつ表示する。

通知中に矢印、回転、配置、オーバーレイ、終了などの操作キーが押された場合は現在通知を閉じ、その入力を消費する。次の入力から通常操作へ戻る。最終ターンでは全通知を閉じた後に結果画面へ移る。

ハイスコアは`HighScoreStore`がローカルJSONへ非負整数の最高点だけを保存する。読み書きやデータ検証の失敗は明示的な例外とし、アプリ層だけがゲーム継続用の表示へ変換する。

## 理由

- 画面遷移とルール状態の責務を分け、Pyxelなしで通知順と結果遷移をテストできる。
- 通知を同じ入力で閉じつつ配置まで実行すると、読み終わった瞬間の誤配置が起きるため、入力を1回消費する。
- 単一最高点だけならフェーズ4の目的に十分で、ランキングなど将来候補を先行実装しない。
- 壊れた保存データを黙って初期化しないことで、不具合やデータ消失を隠さない。

## 検討した代替案

### 通知へ表示時間を設ける

- 利点: 操作なしで自動的にゲームへ戻る。
- 欠点: 読む速度を強制し、待ち時間が集中を切る。
- 不採用理由: プレイヤーの操作で即座に戻る方針に合わない。

### 通知解除キーをそのまま盤面操作へ適用する

- 利点: 入力回数が1回少ない。
- 欠点: 通知に隠れた盤面で意図しない移動・回転・配置が起きる。
- 不採用理由: 1入力の短縮より操作の安全性を優先した。

### 複数スロットやオンラインランキングを保存する

- 利点: 長期的な競争やプロフィール管理に使える。
- 欠点: データ形式、UI、通信などフェーズ5以降の判断を先取りする。
- 不採用理由: フェーズ4のローカル最高点を超える。

## 影響

- コード: `ui.py`が画面・通知、`persistence.py`が保存を担当し、`app.py`が両者を接続する。
- テスト: 通知キュー、オーバーレイ制約、結果遷移、入力消費、保存検証をPyxelなしで確認する。
- UI: `Tab`で川、`Y`で役、結果画面で`R`再開とする。
- 将来の変更: 通知のアニメーションは`Notice`データを保ったまま描画側へ追加できる。
- 移行作業: なし。

## 確認事項

プレイテストで通知解除にもう1入力必要なことが重く感じる場合は、移動キーだけを同一フレームで適用するなど、キー種別ごとの扱いを再検討する。
